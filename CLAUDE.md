# Virtual God Island — инструкции для AI-агента

Этот файл — главный свод правил для любого AI-ассистента (Claude Code и др.), работающего в репозитории.
`AGENTS.md` ссылается сюда. При конфликте правил приоритет: прямое указание пользователя → этот файл → `docs/*`.

## 0. С чего начать каждую сессию
1. Прочитать `docs/ROADMAP.md` — текущий этап, раздел «Следующий шаг», «Известное».
2. Прочитать `docs/GAME_DESIGN.md` — концепт и уже принятые решения по игре.
3. Просмотреть `CHANGELOG.md` (раздел `[Unreleased]`) и `docs/decisions/` — что сделано и почему.
4. По коду задачи — `docs/ARCHITECTURE.md` и `docs/CONVENTIONS.md`.
5. `git log --oneline -20` — последние изменения.

## 1. Честность и формат ответов
- **Только правда.** Если не уверен — сказать «не уверен» сразу и предложить способ проверить. Не выдумывать API,
  версии пакетов, результаты команд. Версии и API библиотек проверять (`node_modules`, `pnpm view <pkg> version`, документация).
- Не писать «проверено/работает», если команда не запускалась. Визуальное поведение клиента без запуска браузера
  помечать как «не проверено визуально».
- Ответы — на русском, кратко и технически точно: сначала решение, потом короткое объяснение.
- Всегда давать шаг проверки (команду).
- Спорные дизайнерские решения (механика, баланс, стиль) — не принимать молча: предложить вариант и спросить.

## 2. Архитектура (не нарушать)
Подробно — `docs/ARCHITECTURE.md`.
- Монорепо pnpm: `packages/sim` (логика), `packages/client` (Three.js), `packages/server` (NestJS, этап 6).
- `sim/` детерминирован и не зависит от рендера: **никаких** `Math.random()`, `Date.now()`, `performance.now()`,
  DOM, `three`, `localStorage`, таймеров внутри `sim/`.
  Случайность — `nextFloat(world)` / `createRng(seed)`. Реальное время — только в `catchUp(world, now)`.
- Состояние `World` — чистые JSON-данные (без классов, `Map`, `Set`, функций, `undefined`-полей, циклических ссылок).
- Каждая механика: сначала `sim/` + тест (vitest), потом визуал в `client/`.
- `client/` читает состояние `sim/` и отправляет в него действия; игровые правила в `client/` не пишутся.
- Изменение формы `World` = изменение формата сейва → поднять версию ключа сейва или написать миграцию (см. ARCHITECTURE).

## 3. Рабочий цикл задачи
1. Понять задачу; при неоднозначности — уточнить. Крупную задачу разбить на шаги.
2. Реализовать минимально нужное. Не делать рефакторинг «заодно» без запроса.
3. Тесты: новая логика в `sim/` → новый тест. Исправление бага → тест, который падал до исправления.
4. Проверка: `pnpm test && pnpm typecheck` (и `pnpm build`, если трогали client/конфиги).
5. Документация — по `docs/DOCUMENTATION.md` (минимум: `CHANGELOG.md` → `[Unreleased]`, статус в `ROADMAP.md`).
6. Коммит по правилам ниже. Push — в назначенную ветку.

### Definition of Done
- [ ] `pnpm test` и `pnpm typecheck` зелёные (результат реально получен).
- [ ] Для новой логики `sim/` есть тесты, в т.ч. на детерминизм, если затронуты RNG/тик.
- [ ] `CHANGELOG.md` обновлён.
- [ ] `ROADMAP.md` обновлён, если сдвинулся статус этапа / «Следующий шаг» / «Известное».
- [ ] `GAME_DESIGN.md` обновлён, если изменилась механика или правило игры.
- [ ] ADR в `docs/decisions/`, если принято архитектурное решение (библиотека, формат данных, протокол).
- [ ] Нет мёртвого кода, отладочных `console.log`, закомментированных блоков.

## 4. Git
- Conventional Commits на английском: `feat(sim): ...`, `fix(client): ...`, `docs: ...`, `test(sim): ...`,
  `chore: ...`, `refactor(...)`, `perf(...)`. Тело — по желанию, на русском или английском, «что и зачем».
- Один коммит — одно логическое изменение. Документация может идти в том же коммите, что и код.
- Не коммитить: `node_modules`, `dist`, сейвы, секреты, `.env`.
- Не переписывать опубликованную историю; не делать `push --force` без явного разрешения.
- PR создавать только по просьбе пользователя (шаблон — `.github/pull_request_template.md`).

## 5. Зависимости
- Добавлять только при реальной необходимости, с обоснованием (в ADR, если библиотека значимая: физика, сеть, ECS).
- Версии пинить точно (`"three": "0.180.0"`, без `^`/`~`). Перед добавлением проверить актуальную версию
  (`pnpm view <pkg> version`), не полагаться на память.
- `sim/` — без runtime-зависимостей (только dev: vitest). Исключение — через ADR.
- `pnpm-lock.yaml` всегда коммитится вместе с `package.json`.

## 6. Команды
```bash
pnpm install    # зависимости (Node 22+, pnpm 9.15.9 через corepack)
pnpm dev        # клиент, http://localhost:5173
pnpm test       # vitest для sim
pnpm typecheck  # tsc по всем пакетам
pnpm build      # сборка клиента
```
Перед коммитом: `pnpm test && pnpm typecheck`. CI (`.github/workflows/ci.yml`) запускает то же + `pnpm build`.
